# H.264 硬件图传路线：已排除的历史诊断

目标路线曾是：

```text
GC2093 CH0 YUV420SP -> K230 VENC H.264 -> TCP -> PC
       CH1 RGB565   -> Blob 视觉 -> UART -> Ti
```

若可用，H.264 可把编码工作从 MicroPython CPU 移走。但在本项目的 **Yahboom CanMV v1.4.3** 上，双通道配置在 `Sensor.set_framesize()` 报：

```text
'Sensor' object has no attribute 'buf_init'
```

所以当前结论是：

- `k230_h264_dual_stream_probe.py` 仅保留作历史证据，**不要部署或重复运行**；
- `k230_final.py` 必须保持 `VIDEO_BACKEND = "jpeg_cpu"`；
- 当前比赛方案是已实测的“640×480 原始采集 → 320×240 控制视觉 + 原始 640×240 管子 ROI、JPEG Q80 图传”；
- 若误运行探针或发生半初始化 Sensor 异常，先在 IDE 执行 soft reboot，再运行主程序；不要在同一次启动中二次创建 `Sensor(2)`。

未来只有在更换为明确支持双通道 Sensor/VENC 的固件，或迁移到 K230 SDK 工程时，才重新评估 H.264/H.265 + RTSP。重新测试不能影响当前 UART 闭环，并需独立建立回退方案。
