# K230 硬件 H.264 路线记录与当前图传配置

以下 H.264 方案曾用于验证是否可将图传从 `RGB565 -> img.compress()` 软件 JPEG 路径迁移为：

```text
GC2093 -> CH0 YUV420SP -> K230 VENC H.264 -> TCP -> PC/PyAV
       -> CH1 RGB565   -> 传统 Blob 视觉 -> UART -> Ti
```

若可用，图传编码将不再占用钢球识别所用的 MicroPython CPU 时间。视频断连仍只影响显示和录像，不会阻塞 UART。

当前 Yahboom `CanMV v1.4.3` 已实测不支持这一路 MicroPython 双通道配置：探针在 `YUV420SP` 的 `set_framesize()` 就触发 `buf_init` 缺失，尚未进入 VENC。因此不再对该固件继续启用 H.264；主程序保持已验证的 `jpeg_cpu`，避免图传试验阻止 UART 视觉控制启动。

该固件对主输出 CH0 还存在兼容性差异：传入 `chn=CAM_CHN_ID_0` 会进入缺少 `buf_init` 的分支。因此探针和 H.264 路径均使用默认 API 配置 CH0；CH1 才显式传入 `chn=CAM_CHN_ID_1`。

## 当前软件推流的正常现象与目标

K230 应依次出现类似日志：

```text
[K230] Camera 640x480 OK
[K230] Vision full-FOV 640x480 -> 320x240
[K230] Video direct 320x240 Q70 @8fps
[K230] Running: vision -> UART; jpeg_cpu video is best-effort only
[K230] PC video receiver connected
```

稳定后重点记录这行：

```text
Loop:... Video:...fps ...KB/s jpeg_cpu Q70
ms/frame cap:... vis:... enc:... net:...
```

验收预期：`enc` 应明显低于原来 VGA/Q50 的约 `59 ms/frame`；视频和控制循环均优先稳定，实际 FPS 以日志为准。

## 若异常，请保留完整日志

| 现象 | 请反馈的内容 | 临时恢复方式 |
| --- | --- | --- |
| K230 显示 `Vision canvas unavailable` | 该行完整异常 | 停止测试；不能以中心裁剪代替全视场视觉 |
| PC 无画面 | PC 端启动日志和 K230 的 `Video` 日志 | 确认 PC 与 K230 均使用最新文件 |
| 视频仍周期断连 | K230 `video socket stalled` 前后 30 行、PC 端断开前后日志 | 保持 `STREAM_PROFILE="control"`，检查热点与 PC 接收端 |
| 视频清晰但不够流畅 | 连续 3 行性能日志 | 比赛保持控制档；展示时才改为 `"clarity"` |

不要在首次验证时同时修改亮度阈值、`Kp/Kd`、摄像头位置或热点信道；先确认视频链路稳定，再做视觉标定。

## 参数调整顺序

1. 比赛先保持 `"control"`；需要图传展示时才改为 `"clarity"` 或 `"quality"`。
2. 热点断连或 `net` 明显升高时，保持 `"control"`，而不是降低内部视觉分辨率。
3. 视频稳定而控制 `Loop` 低于 15 FPS 时，先发送日志；不要为了图传关闭 `VISION_ENABLE`。
4. 该固件目前不启用硬件编码；VGA/Q50 的约 9 FPS 是已测到的软件 CPU 上限，并非 Ti/UART 问题。
